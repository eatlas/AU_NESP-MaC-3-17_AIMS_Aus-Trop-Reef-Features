## [v1-0] - 2026-07-13

### Notes

### 2026-10-29
Corrected the area calculation projection in `06-crosswalk.py` and `A01-summary-stats.py` from EPSG:3112 (GDA94 / Geoscience Australia Lambert, a conformal projection) to EPSG:3577 (GDA94 / Australian Albers, an equal-area projection). This changes the published `Area_km2` values and the summary areas used in the technical report, without changing feature geometry or classifications. Existing outputs must be regenerated by running stage 06 followed by A01.

#### Erratum: area values in previous dataset versions

Previous dataset versions generated using EPSG:3112 contain projection-related errors in `Area_km2`. Earlier descriptions of EPSG:3112 as an equal-area projection were incorrect. This also affects totals, comparisons and other statistics calculated from those area values, including areas calculated by the earlier A01 analysis. Feature boundaries, identifiers and classifications are not affected by this error.

The magnitude of the error varies with location and the features included in a calculation. As an indication of its effect, recalculating the same 25,217 features in the current v1-0 build reduced the summed source area from 76,092.7749 km² to 75,207.9064 km², approximately 1.16% lower. This comparison is for the current build, not a measured correction for each previous release. A single percentage correction should not be applied to older datasets.

Users analysing a previous release should recalculate feature areas from that release's geometries in GDA94 / Australian Albers (EPSG:3577), or use the corrected v1-0 output where appropriate. Area-based results derived from affected releases should be reviewed and recalculated. The corrected workflow does not retrospectively update previously distributed files.

### 2026-10-28
The processing workflow now incorporates v1-2 of the North and West Australian Features (NW-Features) dataset.

Updated `02c-patch-CS-Features.py` to use the new `CS_RB_Type_L3_v0-3` source column in the NW-Features v1-2 crosswalk, rather than `RB_Type_L3_v0-3`. This accounts for the slightly different treatment of Atoll Platform in the two source datasets. In the Coral Sea mapping, Atoll Platform excludes separately mapped coral reefs and translates to Oceanic Platform under scheme v0-4, classified as Sediment at L2. In the NW-Features v0-3 classification, Atoll Platform includes sediment and reef hard substrate and translates to Coral Reef Bank under scheme v0-4, classified as Coral Reef at L2. The separate source columns preserve both interpretations.

### 2026-09-03
Updated the processing workflow so that the GBR component is based on the latest GBRMPA Great Barrier Reef Features dataset, rather than the stale GBR Features included in the 2016 integrated Torres Strait and GBR Features dataset. Although the reef boundaries have changed very little since 2008, the current source includes updates to reef names and identifiers that should be carried into this release.

Added `01d-refresh-TS-GBR-Features.py` as a new preprocessing stage before `02a-patch-TS-GBR-Features.py`. The script retains the 3927 records marked `DATASET='TS Features'` from the existing integrated layer and replaces all records marked `DATASET='GBR Features'` with the latest GBRMPA records. GBRMPA features with a `LABEL_ID` beginning with `99-` are excluded because they overlap the remapped Torres Strait coverage. The two mainland-associated features with `LABEL_ID='99-000'` are retained. The latest GBRMPA data are transformed from GDA2020 (EPSG:7844) to GDA94 (EPSG:4283), and the classification fields needed by subsequent processing are reconstructed from `FEAT_NAME`. Attributes generated during creation of the old integrated dataset, but not needed by the current workflow, are not carried forward.

The latest GBRMPA shapefile contains incorrectly encoded shell and hole relationships. The refresh stage repairs 532 invalid geometries retained after the Torres Strait filter and validates the written output. The resulting 9050-feature intermediate is saved to `working/01/TS-GBR-Features-latest.shp` and is now the source layer used by `02a-patch-TS-GBR-Features.py`. Running the patching script against the refreshed source also identified two obsolete removal markers for Curtis Rock and Curtis Rock Reef. These markers were removed because those source features are no longer present in the latest GBRMPA dataset.

### 2026-08-27
I create an 'inshore-extent' shapefile that corresponds to the bounding polygon of the UQ gbr10_reef_outlines_inshore_2025 dataset. The GBR remapping done under this project currently covers a similar level of coverage, plus a light coverage of the offshore reefs. We therefore adopt this bounding extent as the region where the remapping is comprehensive. i.e. we have remapped every reef within the same bounding extent as the UQ gbr10_reef_outlines_inshore_2025 dataset. This will allow the new mapping to be a drop in replacement and or a direct comparison. The two different reef mapping datasets are different. The Aus-Trop-Reef-Features is closer to a habitat map and more suitable for scientific research, while the gbr10_reef_outlines_inshore_2025 is more aligned with reef management polygons, rather than the reef boundaries themselves. It has a greater clustering distance and often includes more sediment areas into the reef boundaries. Its key limitation is the lack of feature classification and so rocky reefs, coral reefs and some sand banks are mapped, but not considered as different. This is fine for considering it as a map of named places, but it does not distinguish what the place corresponds to. The GBR mapping in the Aus-Trop-Reef-Features focuses on distinctly mapping sand banks, rocky reefs and coral reefs as distinct regions, and so where they are neighbouring they are separated into different polygons. The mapping is tighter around these habitats and so more parts become separated. In general features are clustered to where they are separated by less than 50 m or so. The goal of the mapping is to not introduce too much sandy areas due to the clustering. The goal is that once you are inside the coral reef or rocky reef that in most cases you should be able to fine hard coral substrate within 100 m of any point. Coral Reef Flats are used to represent areas of the coral reefs where it is mostly largely sandy areas with a low biomass, but the region is still associated with the surrounding or neighbouring reef. It is a region that was created as a result of the reef, and there is like a hard substrate underneath the sandy areas. It is also used to infill areas of a reef that are mostly sandy, have a low biological activity but are what you would consider to be part of the reef, i.e. they make the boundary of the reef (when combining the Coral Reef Flat and Coral Reef features) as expected. For the Coral Reef Flat we do not try to determine the difference between vegetation growing on the reef surface (seagrass, algae) and coral. From a mapping perspective the Coral Reef Flat focuses on areas that are within the coral reef boundary that have little visible biological activity. We also don't try to very finely map this separation between high and low activity. This is because it the transition between the two classifications (Coral Reef and Coral Reef Flat) are often quite ambiguous because you might have a coral rubble area that slowly thins out and transitions to sand. The goal of the COral Reef Flat mapping is to concentrate the Coral Reef classified area as meaning higher levels of coral substrate.
We find that quite a few coral reefs are surrounded by sandy slopes, presumably from the accumulation of sand from the coral reef itself. This means that the coral reef is not coral reef substrate all the way to the seafloor, but that the coral reef hard substrate stops at a shallower depth. In general we typically include some of this sand, typically up to 50 m or 10 m depth in the outer edge of the coral reef. We do this because this area is likely highly biologically connected to the reef.

### 2026-08-19
Focusing mainly on fixing the rocky reefs around the Whitsundays and ensuring the Attachment attribute is consistently applied. I have found that for fringing rocky reefs it is often difficult to decide whether they should be classified as intertidal, since by definition they will meet the intertidal zone on the landward side, or to classify them based on the predominant depth, excluding the 10 - 20 m strip that corresponds to the land side. In this way a rocky reef that has an almost cliff landward side would then be classified by the shallowest portions of the region under the water. An additional complication is that in many location the red channel is greatly suppressed close to the boundary of islands. This makes using the 'Sentinel 2 Red' approach difficult for depth estimates. In this case we rely more on the imagery from Queensland Globe and Google Earth, as well as the likely structure based on the reef type.
Excluding the landward side of the rocky reefs does lead to a complication for small rocky reefs. A small rocky reef that is just high enough to occassionally pop out of the water at low tide would be classified as an isolated, intertidal rocky reef, but a rocky feature that is slightly taller, where there is a portion that is always out of the water would be classified as a fringing, very shallow rocky reef. It is fringing because it is surrounding an island, and it is no longer intertidal because the central shallowest portion is excluded from consideration. This feels slightly contraditory. We use the Coastline 50k as an indication of whether there is an island and thus we treat the small rocky reef as isolated (no island) or fringing (an island). For the depth estimate I typically based the classification on the shallowest couple of percent of the area of the feature.

Added processing to `05-add-depth.py` so that the Lowest Tidal Prediction (LPT) from the tidal statistics dataset is subtracted from the Digital Elevation Model (DEM) so that a prediction of the depth relative to Lowest Astronomical Tide is estimated. If a feature has a 90th percentile that is above 0 m LAT then it is classified as Intertidal. This processing worked well, however we did find a follow up problem with the cross walk validation `06-crosswalk.py`. The automated depth estimate flagged a Oceanic Platform that is 8 km north west of Portlock Reefs (PNG waters) as intertidal. The Oceanic Platforms are generated by taking the Oceanic Atoll Platform dataset, then clipping out the Coral Sea reef boundary mapping. The Oceanic Atoll Platform dataset does not include a manual depth estimation and so the classification is based on the DEM model. Unfortunately the DEM is positionally offset by several hundred metres, and it only 250 m pixels for the problematic location. As a result the Oceanic Platform gets the depths of the Intertidal reef tops. This creates a false estimation of depth.

To get around this problem of the DEM model we could solve the problem in two ways: 1. only generate a warning for the invalid classification combination, or 2. It would kind of make more sense to 'clip' the shallow nature of the Oceanic Platforms to 'Very Shallow' if it is 'Intertidal', however in practice the only two feature we have seen where this rule will apply correspons to Oceanic Platforms that have steep sides and so any errors in the DEM result in large errors in the depth estimate of the feature. 1. Features in the new mapping replace all features that they overlap in the old mapping by at least 1% IoU. Using a small IoU helps to prevent features from being deleted where the overlap is very very small. This overlap test allows the remapping to understand what features were merged together or replaced.
2. Where the replacement reef does not overlap the old reef mapping (this occurs when there are large positional errors in the old mapping), then we need to ensure the link between the replacement and the old feature. For this we will copy over the CODE value of the feature we are replacing. This is still awkward, however this should be a relatively infrequent adjustment.
3. Where there is a false reef in the original mapping that needs to be removed then this done with a separate point shapefile that just indicates these removals. This is a subset of the operations recorded in the `Complete-GBR-FeatureType-Override.shp`. 

This means that in the new mapping most features will not have a CODE assigned. This will only be allocated in post processing. Where a CODE is assigned in the replacement mapping it indicates that the original feature should be removed. Where no CODE is assigned then the feature is either a replacement, if it overlaps with any existing features, or a new reef feature. 

This approach removes the capability to simply change the classification of an existing feature, without copying it over to the new mapping file. I don't think this is too much of a problem as most features need remapping their boundaries. It will just mean that existing reclassifications, done in v0-1, will need to be repeated.

##### **Transition to new files**
The steps in this adjustment were:
1. Making a copy of Complete-GBR-ExtraFeatures to AIMS_GBR-Ts-Features_Edit_v1-0. 
2. Adding attributes: 'FeatConf', 'TypeConf', 'DepthCat', 'DepthCatSr', 'RB_Type_L3', 'Attachment', 'EdgeSrc', 'EdgeAcc_m'
3. Assigning the Value Map for each of these attributes based on the `in\QGIS-value-maps` to make the editing more efficient.
4. Applying a cross walk from the FEAT_NAME classification to sensible attributes in RB_TYPE_L3. This was done using the field calculator.
```
CASE
    WHEN "FEAT_NAME" = 'Reef' THEN 'Coral Reef'
    WHEN "FEAT_NAME" = 'Rock' THEN 'Rocky Reef'
    WHEN "FEAT_NAME" = 'Bank' THEN 'Sand Bank'
    ELSE NULL
END
```
5. Create the point shapefile to record reef removals. Use the Query Builder on `Complete-GBR-FeatType-Override` to retain just the removals:
```
"FEAT_NAME" = 'Remove'
```
Then export as `GBR-FeatType_Reef-removals.shp`, changing the attribute `FEAT_NAME` to `ACTION`.
